# ADR-141: The Repository Is Prepared for Either Production Host; the Host Choice Stays the Owner's

**Date:** 2026-09-29
**Status:** Implemented and locally qualified (macOS, arm64 Debian 13 container, systemd 257 in a container); not deployed. The host choice is open.
**Requirements:** FR-070 (encrypted backups, restoration proven), NFR-003 (RPO and RTO proven by drills), NFR-013 (upgrades need a backup and a rollback artifact).
**Changes a foundation:** the production host. Until now every host script assumed the office Mac (launchd, Docker Desktop, BSD tools, stamps of that Mac's volumes in git). This ADR makes the scripts host-neutral; it does not move production.
**Builds on:** ADR-035 (file store and its backup), ADR-053 to ADR-057 and ADR-134 (paired Restate backup and the clean-host restore), ADR-081 (archive lock), ADR-127 (watchdog recovery of a cut-off backup), ADR-135 (only the live worker colour polls Telegram).

## 1. Context

The hosting plan (`plans/hosting/PRODUCTION_HOSTING_PLAN.md`, 2026-09-29) recommends moving production off the owner's MacBook, preferably to a rented arm64 Linux server (netcup VPS 4000 ARM or Hetzner CAX41), with a Mac mini in the office as the fallback. Section 10 leaves the choice, the purchase and the cutover window to the owner. Whichever is chosen, the repository could not run on the new host as it stood:

- **Two scripts fail on Linux** (plan section 3.6, reproduced again for this ADR in an arm64 Debian container with GNU coreutils 9.7). `infra/security/local_state_audit.sh` read modes with `stat -f '%Lp' f || stat -c '%a' f`. On Linux `stat -f` means "file-system status": it prints six lines and fails, both outputs land in the variable, and `$((8#$mode & 8#077))` stops `deploy.sh` under `set -e`. `infra/backup/nightly_backup.sh` had the same form for the dump's size and `stat -f '%z'` with no fallback for the file store's bytes, so every night would fail.
- **The volume stamps were this Mac's.** `infra/docker/.postgres_volume_created` and `.restate_volume_created` were tracked in git with the Mac's volume creation times. `deploy.sh` steps 1b and 1c refuse a volume whose creation time differs from the stamp, so every other host refused to deploy; correcting the files made the checkout dirty, which `deploy.sh` also refuses.
- **`validate_pack.py` failed in every fresh clone.** The known trap was a link into a gitignored `output/audits/` report; on this branch that report is tracked and the link resolves. What still failed, in a real `git clone`, was the manifest: `MANIFEST.json` and `SHA256SUMS.txt` listed four files of `.pytest_cache/`, which exists only where `python3 -m pytest infra/backup` has been run from the root. `deploy.sh` step 4 runs the validator.
- **Scheduling, Docker and wording were Mac-only.** The watchdog, the nightly backup and both drills are launch agents; the watchdog starts Docker with `open -ga Docker`; its disk alert sends the reader to macOS System Settings; `disk_cleanup.sh` used BSD `date -v` with a GNU fallback; several scripts hash with `shasum`, which a Linux host has only with perl.
- **The archive never leaves the host it protects.** `nightly_backup.sh` says so itself: a synchronized folder is not an off-host copy.
- **A cutover can leave two live hosts.** The old host's watchdog restarts its stack within five minutes, and two hosts would poll the same Telegram bot (plan sections 7.4 and 8).

## 2. Decision

**The owner chooses the host. The repository runs on either, and nothing changes on the Mac until a setting or a marker says so.**

1. **One place for host-specific commands.** `infra/ops/host_lib.sh`, sourced by the host scripts, chooses by `uname` once: GNU `stat -c` or BSD `stat -f` (as `HAWA_STAT_SIZE` and `HAWA_STAT_MODE` command arrays, so `xargs` can use them), GNU `date -d` or BSD `date -v`, and `shasum -a 256` where it exists, else `sha256sum`. Never `bsd-form || gnu-form`. `local_state_audit.sh`, `nightly_backup.sh`, `restore_drill.sh`, `backup_restore_drill.sh`, `drill_restore_swap.sh`, `disk_cleanup.sh`, `deploy.sh`, `scripts/enforce_release_gate.sh` and `scripts/disaster_recovery_drill.sh` use it. On macOS each resolves to the command the script ran before.
2. **Volume stamps are host-local.** `~/.hawa/volume-stamps/<volume>.created` (`HAWA_VOLUME_STAMP_DIR`), directory 0700, files 0600. The two repository files are untracked and gitignored. `deploy.sh` uses the host-local stamp; failing that it adopts the old repository file's value once (logged); failing both it records the volume's creation time and goes on, exactly what it did before for a missing stamp file. A mismatch is refused as before.
3. **A host role.** `~/.hawa/host-role` (first word) or `HAWA_HOST_ROLE`: `production` (or nothing: today's behaviour), `standby` (a host being prepared) or `retired` (the host production left). On standby and retired hosts the watchdog never starts Docker or a `hawa-production` container and never touches Restate, and reports (and alerts about) production containers running there; `deploy.sh --apply` refuses before any step, and pre-flight records no volume stamp; the nightly backup, both drills and the off-site copy skip with a log line. Any other value is refused everywhere.
4. **Linux scheduling.** `infra/ops/install_systemd_units.sh` installs `infra/ops/systemd/*.in` as system units run by the checkout's unprivileged user (in the `docker` group), so they run from boot without a login: the watchdog one minute after boot and every five minutes, the nightly backup at 03:30 Asia/Baghdad with `Persistent=true`, the schema drill on Sundays at 04:00, the data drill on the 1st at 05:00 and the off-site copy at 05:30. Settings come from `/etc/hawa/backup.env` (root, 0600, read by systemd before it drops privileges), written once from the variables the launch agents carry and never rewritten; logs go to `~/.hawa/logs/<launch agent label>.log`. `--uninstall` and a side-effect-free `--render` exist. `install_launch_agents.sh` stays for Macs.
5. **The watchdog on Linux** reads `systemctl is-active docker` instead of opening Docker Desktop: it waits while the service is starting, and otherwise reports it (stopped, or active but unreachable by this user). An unprivileged pass cannot start a system service, and on a server Docker is enabled at boot. The disk alert names "the production host" and gives a macOS or a Linux hint.
6. **Off-site copy.** `infra/backup/offsite_copy.sh` (with `offsite_copy.py`) copies the newest complete encrypted recovery set (the dump and its checksum, the file manifest and every pack it needs, and the paired Restate copy, authenticated with the archive key without decrypting anything) to `HAWA_OFFSITE_DEST`: an absolute path, or `[user@]host:path` over rsync and SSH, such as a Hetzner Storage Box. It holds `archive_lock.py --mode shared` for the whole run and waits for a nightly still holding the archive, verifies every file at the destination (SHA-256 read-back, or `rsync --checksum --dry-run`), writes the set's receipt last, is idempotent, and keeps `HAWA_OFFSITE_KEEP` sets there, deleting only names it writes and a pack only when no kept receipt lists it. Unencrypted archives are refused. Each run logs `COPIED`, `CURRENT` or `FAILED` to `snapshots/offsite.log`; once that file exists, `backup_status.py`, and so the watchdog, reports a failed copy, a copied set older than 30 h, or a newer nightly not copied within 6 h. A launch agent and a systemd timer run it at 05:30. With `HAWA_OFFSITE_DEST` empty it does nothing and writes nothing, which is the Mac today.
7. **Tool caches are never package files.** `validate_pack.py` skips `.pytest_cache`, `.mypy_cache` and `.ruff_cache` anywhere, and the manifest was refreshed without them.

### Why this and not something else

- **Choosing by `uname`, not by trying.** A failed BSD form can print output before failing, which is exactly how the plan's two bugs happened.
- **Keeping "record and continue" for a missing stamp.** Refusing a host with no stamp would block every first deploy; the stamps exist to catch a volume recreated between two deploys, and the second deploy on a new host is checked. The one deploy after the merge on the Mac is covered by the adoption step and by the one-time copy in `infra/docker/README.md`.
- **A host-local marker, not a check of "is the other host alive".** The other host may be unreachable, and a network check can fail open. A file the operator writes during the cutover fails closed and needs no network.
- **System units with `User=`, not user units.** User units need lingering and a user bus, and could not read a root-only settings file. System units run from boot like the plan requires.
- **rsync for SSH destinations.** Storage Boxes speak rsync over SSH; `--checksum --dry-run` compares content on both sides without a remote shell. A local path is read back and hashed.

## 3. Consequences

- On the Mac nothing changes until the lead merges and redeploys, and even then: the four existing launch agents render byte-identical (checked against the installed plists), `host_lib.sh` resolves to the same `stat -f` and `shasum -a 256` under the agents' PATH and `/bin/bash` 3.2, the Mac has no role marker, and the off-site agent does nothing until configured.
- **One-time step on the Mac when this is merged** (merging deletes the two tracked stamp files from the main checkout): copy them to `~/.hawa/volume-stamps/` first (`infra/docker/README.md`, "One-time step on the office Mac"). If that is forgotten, the next deploy records the current creation times and protects every later deploy.
- **A brand-new host** creates its two external volumes (empty, or restored), runs `deploy.sh`: pre-flight records the two stamps (unless the host is marked standby) and stops only at what the host lacks (configuration, model files); every later deploy checks them.
- The move gains two explicit operator steps: `standby` on the new host until the cutover, `retired` on the old host right after the final backup (`runbooks/10_backup_restore.md`, "Moving production to another host").
- Off-site copying adds an expected daily outcome once enabled; turning it off needs both the setting and `offsite.log` removed.
- A Linux host needs `rsync` for an SSH destination and PyYAML for the validator; the requirements are listed in `infra/ops/README.md`.

## 4. Verification (2026-09-29)

- macOS: `python3 -m pytest infra/backup` (104 passed, 1 skipped: the rsync-transport test needs GNU rsync; macOS ships openrsync); the new and the existing watchdog, deploy and host tests in `packages/testkit/test` (`host-portability`, `deploy-sh-host-local-state`, `watchdog-host-role`, `host-scheduling`, `validate-pack-tool-caches`, `watchdog-*`, `deploy-sh-*`); `packages/db/test/blob-backup.test.ts` and `blob-prebackfill.test.ts`, which run the changed `nightly_backup.sh`, `restore_drill.sh` and `disk_cleanup.sh` end to end against the test server (22 passed); the launch agents rendered from the installed plists' settings and compared with them (identical); the full suite (see the proof file).
- arm64 Debian 13 container, GNU coreutils 9.7, bash 5.2, no network (`scripts/proofs/linux_host_readiness.sh`, 29 checks): the plan's `stat` failure reproduced with the old form; `host_lib.sh`; the audit; two whole nightly backups against PostgreSQL in the container through a `docker exec` shim (encrypted archive, packs, `blob_bytes` read with GNU `stat`); `backup_status.py`; a retired host's skip; the off-site copy to a path and through GNU rsync 3.5, verified and decrypted back; `pytest infra/backup` (104 passed, one Node-22-only test deselected); the watchdog's Linux Docker check and retired pass; `deploy.sh` on a fresh host up to its configuration check (both stamps recorded, a recreated volume refused, a retired host refused before any step); the units rendered and passed by `systemd-analyze verify`, and their calendars.
- systemd 257 as PID 1 in a throwaway container (`scripts/proofs/linux_systemd_install.sh`, 11 checks): install, five timers active, settings file root 0600 seeded from the calling environment, logs owned by the job user, the watchdog timer firing by itself, the nightly service reading `HAWA_HOST_ROLE` from the settings file, the off-site service doing nothing unconfigured, jobs running as the user, reinstall keeping the settings, uninstall.
- A fresh `git clone` of this branch passes `python3 scripts/validate_pack.py`, with and without `refresh_manifest.py` first.
- Results: `plans/hosting/LINUX_READINESS_PROOF.json`.

**Not proven:** a real server; Docker Engine on Linux running this stack (images, Compose profiles, bind mounts); `deploy.sh --apply` on Linux; an SSH destination (the rsync transport was exercised against a local path, and no SSH key was created for a test); the cutover and rollback. They belong to the rehearsal in the plan's section 7.3.

## 5. What only the owner decides

The hosting plan's section 10: the option (arm64 cloud server or Mac mini), the provider and payment, the domain and Cloudflare account, the off-site storage (for example a Storage Box), the team list for Access, and the cutover window. This ADR records none of those choices.
