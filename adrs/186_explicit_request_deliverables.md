# ADR-186 — Explicit request deliverables

Date: 2026-10-01
Status: accepted for implementation; qualification and live rollout pending
Requirements: FR-001, FR-002, FR-004, FR-005, FR-033, FR-060, FR-063, NFR-001, NFR-006
Sources: docs/09_MESSAGING_AND_OFFICE_INBOX.md; docs/05_CREATIVE_ENGINE.md;
docs/10_WORKFLOW_RELIABILITY.md; MASTER_SPEC.md; ADR139/184/185.

## Evidence

The remaining ordinary red scripts show a two-design message opening one automatic
task, and a forwarded event request named after its Date line. S022 now requires
two real requests/runs, their requested dimensions and isolated event facts; a
single manual fallback cannot satisfy it. S031a checks the actual persisted title.

## Decision

Extend ADR139's immutable one-source decision and independent lifecycle siblings
to explicit deliverables. A pure domain policy reads an explicit bounded count,
numbered/role sections or distinct formats requested together. No model authorizes
task count, client scope, dimensions or paid work. Original source evidence is
retained; each child gets its own selected source words, stable ordinal identity,
client and canvas. Existing language sibling identities and replay remain intact.
One verified message has one immutable decision; repeated delivery creates no
additional child for an explicitly requested deliverable. FR004's existing
per-language exception extends to these explicit children, not ordinary chatter.

At most eight deliverables are admitted together. A larger request is refused
visibly before opening tasks; it is never silently trimmed. The worker advertises
its bound, validates the entire response and refuses duplicate/missing children;
a decision beyond a draining worker's bound is never replayed as a smaller set.
The ordinary daily and financial limits remain per task, with saved manual
decline evidence when they prevent an automatic run.

Where a count is explicit but allocating its factual content is ambiguous, preserve
that many independently identified manual tasks with the full source, a structured
details-required reason and office alerts. Do not spend on guessed fact allocation.
Clear allocations must produce all their automatic tasks: this fallback cannot
replace the S022 proof or be claimed as complete autonomous semantic interpretation.

An early hold of the original brief applies to all its children before dispatch.
Current sender/chat/topic scope, task version/revision and human resume continue
to govern each child. Reply/edit/photo/source targeting must resolve an individual
child or expose ambiguity, never silently choose the first sibling.

Job names prefer an event subject explicitly present in the request when the copy
starts with metadata. This changes the operating title, not submitted factual copy.
No subject is invented, and ordinary supplied headlines retain precedence.

## Verification required

Both red scripts; pure policy positive/negative/count/literal-copy cases; real Core
task count, client/format/fact isolation, source replay and altered bytes; worker
complete-bundle validation and crash/replay; all-child holds; daily decline and
ambiguous-source diagnostics; full sealed suite, types, egress and traceability.
Native/Canva/real-human quality and coordinated live rollout remain separate gates.


## Connected boundary findings

The first connected controls caught obsolete worker POST expectations and an invalid-canvas mutation test that was rejected by the envelope before canonical comparison. These were corrected without bypassing either guard. Several-child paid-ledger evidence also exposed that the existing hold grammar recognized only singular pronouns; plural whole-job holds now use the same anchored original-brief policy.

A shared source edit cannot be forwarded as an unbound office message: doing so would leave every child's future delivery without the existing late-change hold. Retain one immutable child note under `updateId:requestId` in the existing routing store, atomically with the edit answer. Desk/office acknowledgements accept this strictly bounded identifier, still require scoped membership in the saved pending notes, and release only the selected child's note. No new table or workflow is added. Preserve the previous per-chat early-hold alert keys; additional diagnostics get separate stable keys.

The pure policy and Core application planner are separated from HTTP transport. Negative client mentions reuse the same routing policy as ordinary intake. The office-wide daily admission transaction locks its counted outbox boundary; previously distinct task locks could count the same available allowance concurrently. Replays use recorded automatic/manual admission instead of re-evaluating mutable limits.
