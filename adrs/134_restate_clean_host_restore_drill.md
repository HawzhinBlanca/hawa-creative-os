# ADR-134: The Restate Backup Is Rehearsed on Its Own Stacks, and a Clean Host Restores One Paired Night

**Date:** 2026-09-28
**Status:** Accepted for local implementation. The drill passed 47/47 checks on disposable stacks (evidence below); production enablement is the owner's decision and the lead's change, and has not happened. The checklist is in `runbooks/10_backup_restore.md`, "Enabling the Restate backup in production".
**Requirements:** FR-070 (encrypted backups, restoration proved on a clean environment), NFR-003 (RPO/RTO), NFR-013, R10 (`docs/10_WORKFLOW_RELIABILITY.md`).
**Builds on:** ADR-053 (guarded single-node Restate backup), ADR-054 (conditional release of the intake switch), ADR-055 (the same-night pair), ADR-056 (retention), ADR-057 (isolated archive boot), ADR-127 (recovery of a cut-off run), ADR-129 (restore into a new database and swap).
**Evidence:** `plans/lean-design-implementation-2026-09-28/R10_RESTATE_BACKUP_RESTORE_PROOF.json`.

## Context

Since 2026-09-28 every Telegram chat runs on the lifecycle path, so every live request's durable state (RequestLifecycle objects, ChatInbox and TelegramSender queues, Delivery workflows, reminder timers) lives in Restate. `HAWA_RESTATE_BACKUP_ENABLED` was off: the nightly archive held PostgreSQL and the file store but no journal. R10 kept one acceptance item open: an isolated clean host restores the matching dump, file archive and Restate archive of one paired night, starts exactly one Restate node and one worker, and representative in-flight invocations finish exactly once.

Two things stood in the way of proving it without touching production:

1. `restate_nightly.py` named production's containers, volume, node, Compose file and database in code, and `nightly_backup.sh` runs it with whatever environment it has. A rehearsal could only run it against production.
2. The archive-boot rehearsal (ADR-057) boots a restored copy on a throwaway volume with no network and deletes it. There was no tool that restores an archive into the volume a restored node will actually run on, and nothing that refused to do so beside a running copy of the same node.

A third problem appeared on the drill's first run: `restate_nightly.py` read Core's switch (`GET /v1/ingress/status`) without the operator bearer, and Core answers every unauthenticated read but its health paths with 401. Every `--plan` and `--apply`, and every watchdog `--recover` that must release a pause, was refused before it touched anything. The unit tests used a fake Docker that never ran the request, so nothing had caught it. Enabling the flag in production as it stood would have failed every night with an alert.

## Decision

0. **The switch status read carries the operator bearer**, as the toggle already did (`CORE_CONTROL` in `restate_nightly.py`; `CoreSwitchWireTest` runs the real request script against a server that refuses a read without it).
1. **Every production target of `restate_nightly.py` can be named by the environment, and defaults to today's value.** `HAWA_RESTATE_BACKUP_COMPOSE_FILES` (path-separated; the first is the file whose digest the manifest records), `_COMPOSE_ENV`, `_COMPOSE_PROJECT`, `_VOLUME`, `_CONTAINER`, `_CORE_CONTAINER`, `_POSTGRES_CONTAINER`, `_NODE_NAME`, `_DATABASE` and `_DRAIN_SECONDS`. An empty value counts as unset; an invalid name is refused before any Docker call. Production sets none of them, so its behaviour is unchanged (tests pin every default).
2. **`restate_restore_rehearsal.py --restore-into VOLUME`** restores an authenticated pair into an existing, empty named volume and keeps it. It refuses while any container mounts the volume, while any running container of the archived Restate image carries the archived node name, or when the volume is not empty; after extracting (offline, `--pull=never`) it re-reads the volume and requires every member's size and SHA-256 to equal the archive's. `--source-volume` names the volume the archive must come from (default `hawa-production_restate_data`).
3. **The chaos harness can run under another project name.** `configureStack()` in `packages/testkit/chaos/driver/stack.ts` and `CHAOS_PORT_*` / `CHAOS_IMAGE_TAG` in `docker-compose.chaos.yml` name the project, host ports and image tag; the defaults are the shared `hawa-chaos` values, so every existing run is unchanged. A project name must still start with `hawa-chaos`, so the kill guard holds.
4. **`packages/testkit/chaos/r10-restore.ts` is the R10 drill.** It runs the real `nightly_backup.sh` with the flag on against a source project (`hawa-chaos-r10s`), twice, and restores the second night onto a separate clean project (`hawa-chaos-r10d`) with the runbook's own procedures: the pair check, the restore-swap block for the dump, the runbook's pack unpacking and `blob-verify`, and `--restore-into` for Restate. The source's fakes container stands for the outside world and survives the loss of the source host, so its ledgers count every effect of both hosts.
5. **The drill freezes the source worker before the capture it restores.** Work the source does after the last backup is by definition outside the recovery point: after a restore it is lost (Telegram forgets confirmed updates) or, for a send whose mark was written after the dump, repeated. Freezing the worker makes "resumes exactly once" a statement about the restore, not about the recovery point. The recovery point is reported separately below.

## Consequences

- R10's clean-host item is proved on disposable stacks on this Mac: a separate Compose project, network and set of volumes, the recorded image IDs, no store of the source mounted. It is not a second machine, and the outside world is the chaos fakes, not Telegram, Canva or Google.
- **Recovery point.** A restore brings back the last paired night. Requests, decisions and sends after it are not in it. Telegram keeps unconfirmed updates for about 24 hours, but the worker confirms each update once Restate accepts it, so updates handled after the backup are not offered again: they are lost, and the requester must resend. A TelegramSender send marked after the dump but journaled before the Restate capture could be sent again. The nightly takes the dump first and the Restate capture later (the drill measured the gap); the two are not one snapshot (`crossStoreAtomic: false`).
- **The nightly pause.** Intake is paused from the start of the Restate step until Restate is healthy again, plus the drain wait when an invocation is running (up to `HAWA_RESTATE_BACKUP_DRAIN_SECONDS`, 300 s by default). Measured with production's 10 s Restate health cadence: 13.6 s with nothing running (Restate unavailable 11.6 s, most of it the health interval), 42.4 s with one invocation running and a 30 s drain. With the default drain a stuck invocation would keep intake paused for about 5 min 15 s. An update sent during the pause waited in Telegram and was handed on once, 3.4 s after the release.
- **Restore time** on this Mac, for small data: 34.5 s from the start of the restore to one Core and one worker healthy; the in-flight work finished 12.2 s later. This is not an RTO for production-sized data.
- The drill found the 401 above and caught its own first misstep: its Restate node name collided with another session's running `hawa-chaos` stack, and `--restore-into` refused. The drill now uses its own node name (`hawa-restate-r10-1`).
- The monthly `restore_drill.sh` still verifies pairs byte for byte only; this drill is run by hand before enablement and after a Restate or schema upgrade.
