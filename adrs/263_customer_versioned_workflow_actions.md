# ADR263 — Customer versioned workflow actions

Date: 2026-10-02. Status: selected; qualification pending.
Requirements: FR-029/032 (docs/05_CREATIVE_ENGINE.md), FR-042 (docs/11_QA_RTL_MULTILINGUAL.md), FR-052 (docs/18_FEEDBACK_LEARNING.md), FR-061 (docs/10_WORKFLOW_RELIABILITY.md), FR-069 (docs/14_SECURITY_THREAT_MODEL.md), NFR-006/011/015 (MASTER_SPEC.md). Current Canva contract and ADR256/259–262 remain binding.

Customers submit explicit revise, answer, seen and cancel actions for their current owned request revision. Core verifies current workspace identity/live client admission, locks that basis and persists an immutable action, exact body/hash, verified requester identity and one canonical outbox command. Same-key retries return the retained receipt; differing content conflicts. One unresolved action per request avoids racing the owner. Generation actions count against the customer's daily job allowance; acknowledgements/cancellation have bounded separate receipt retention limits.

The signed web gateway carries only references. It verifies the retained command through Core and sends to the existing private RequestLifecycle object. That object serializes actions with design outcomes. Core rechecks ownership/basis and performs the action transaction, retaining a projected/refused receipt; RequestLifecycle adopts the verified result, starts the existing DesignRun when appropriate and records applied acknowledgement. Durable lost replies reuse receipts. Revocation prevents new work; already committed projections can be reconciled without fresh generation authority.

Revision/answer reuses the existing requester revision intake projection with a separately verified web source. The current task's exact factual copy, format, client, ordered original photos and photo policy remain authoritative; an explicit replacement exact-copy field is retained separately as the requester's live text. Direction alone cannot rewrite facts. Customer revisions are one-time feedback, never automatic taste/rule promotion. A current captured draft may be revised from in_review or manual; answers name the actual current web question message. Native amendment, QA, budget and editable-source gates remain intact.

Seen means an explicit user acknowledgement of that current question, with its actual immutable web message UUID. It is neither a Telegram send confirmation nor inferred reading from page load. Cancellation closes only unapproved active requests through the same task transition/revision ledger; already admitted provider calls settle normally. Customer acceptance is a later separate policy and cannot become staff approval/publication.

Browser action drafts retain exact payload/key per user/request across uncertain outcomes, show queued/projected/applied/refused truthfully and never auto-resubmit. Current basis changes, stale questions, lost access and conflicts have explicit recovery. Public generation/readiness remains disabled until full hosted customer admission.

Acceptance: real scoped PostgreSQL/concurrent retry/quota/revocation/stale-question/task/copy/photo controls; mounted HTTP; private durable SDK handoff and genuine receipt replay; worker owner-state adoption/cancellation/seen/reminder checks; actual browser uncertainty reload and revision/answer/cancel flow. Doubled provider/browser transport is not public/native visual acceptance.
