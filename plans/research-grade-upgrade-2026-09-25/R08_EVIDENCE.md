# R08 — Chat decision acknowledgement containment

**Date:** 2026-09-25. **Status:** in progress. This is a false-acknowledgement repair, not the lifecycle decision implementation.

The public `POST /tasks/:taskId/chat-approval-action` route checked whether an interactive button named the current revision and whether the actor role was allowed, then answered HTTP 200 with `accepted: true`. It did not insert an approval in PostgreSQL or signal a durable review workflow. When a task had no revision, the route substituted the fictional `rev-1`; an action naming `rev-1` therefore received 200. Neither response represented a real decision.

Two isolated-PostgreSQL negative controls reproduced HTTP 200 before the changes: one for a revisionless task and `rev-1`, the other for a valid revision and a button that was only validated. The route now refuses missing current revisions with 412, invalid button revision IDs with 422, and stale buttons with its existing 409. A valid button receives 501 with an explicit statement that no approval was recorded and directs the operator to the durable Desk decision endpoint. The test checks that the task still has no approval. This closes false success at the public boundary while the route is not connected to the database decision transaction.

## Second pass — one transaction and one version per Desk decision

**Source:** `471e7a5` (2026-09-25). The Desk decision route called `RevisionRepository.recordApproval`, which already commits the approval row, revision status, task state/version and immutable `design.*` event in one transaction. It then called `TaskRepository.transitionState` in a separate transaction, advancing the task version again and appending a redundant `task.state_changed` event. A new isolated-PostgreSQL regression failed before repair: one approval advanced version 2 → 4 when 2 → 3 was required. The second transition also swallowed errors after a success response.

The route now uses the repository transaction as the sole state transition. The repair budget formerly applied by the second transition was moved into that transaction: after inserting a revision request, the locked task's request count determines `revision_requested` for the first two and `failed_operator` for the third. The regression now proves one version increment and exactly one `design.approved` event; existing cross-Core and repair-budget tests prove the third request is still routed to an operator.

## Third pass — durable Desk action identity

**Source:** `43512ea`; additional restart-shaped test `3bb4794` (2026-09-25). The Desk now sends a UUID `Idempotency-Key` with an approval or revision request and retains it while the screen is mounted if a network error prompts a retry. Core binds the key to the task, revision, authenticated actor and exact request body by a SHA-256 fingerprint. An already committed, identical action returns the existing decision ID; a reused key with different intent returns 409. The repository repeats the lookup under the locked task row, so simultaneous requests serialize to one approval, one event and one version increment. Invalid keys and non-object bodies are refused before any decision write. A client approver without a resolved assigned-client match is refused, including on replay.

The red-before isolated-PostgreSQL test showed a lost-response retry returning 409 after a successful approval. Green-after checks the same key through a **new Core instance**, verifies the original decision ID, unchanged task version and one approval row, and checks a changed payload is rejected. A simultaneous revision-request test produced statuses 201/200 with one ledger row and one version increment. The Desk API test checks that its key reaches Core; escalation replay uses the decision actually stored (`revision_requested`). The exact source tree before the additional test-only commit passed **408 files / 3,080 tests**, **4 files / 48 tests skipped**; the new Core-instance test then passed in isolation. Full source/script/test TypeScript checks and blueprint **741/0/0** passed on the source tree. The action ID is currently kept in the mounted Desk screen, so a browser reload does not preserve it; a refreshed task still reads PostgreSQL truth, but retry equivalence across browser reload is not proven. A freshly constructed Core is not a killed Restate process. No live double click, deployed-image replay, RequestLifecycle gate, or chat approval has been demonstrated. R08 remains in progress.
