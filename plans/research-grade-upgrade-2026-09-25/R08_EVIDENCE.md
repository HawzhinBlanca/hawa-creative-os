# R08 — Chat decision acknowledgement containment

**Date:** 2026-09-25. **Status:** in progress. This is a false-acknowledgement repair, not the lifecycle decision implementation.

The public `POST /tasks/:taskId/chat-approval-action` route checked whether an interactive button named the current revision and whether the actor role was allowed, then answered HTTP 200 with `accepted: true`. It did not insert an approval in PostgreSQL or signal a durable review workflow. When a task had no revision, the route substituted the fictional `rev-1`; an action naming `rev-1` therefore received 200. Neither response represented a real decision.

Two isolated-PostgreSQL negative controls reproduced HTTP 200 before the changes: one for a revisionless task and `rev-1`, the other for a valid revision and a button that was only validated. The route now refuses missing current revisions with 412, invalid button revision IDs with 422, and stale buttons with its existing 409. A valid button receives 501 with an explicit statement that no approval was recorded and directs the operator to the durable Desk decision endpoint. The test checks that the task still has no approval. This closes false success at the public boundary while the route is not connected to the database decision transaction.

The focused approval integration file passed **13 tests**. The fixed-tree full suite passed **406 files / 3,040 tests**, with 4 files / 48 tests skipped. TypeScript checks passed and blueprint validation reported **725 pass / 0 warning / 0 failure**. The release manifest will be resealed at this source checkpoint; no production flags or live workflows were changed.

R08 remains **in progress**. A chat decision still cannot be recorded through this endpoint. The complete slice must route Desk and chat decisions through one expected-revision, server-authorized PostgreSQL/RequestLifecycle transaction with append-only reason, restart replay and duplicate-action tests. The existing normal Desk decision endpoint remains the available approval route. No deployment or live decision was tested.

## Second pass — one transaction and one version per Desk decision

**Source:** `471e7a5` (2026-09-25). The Desk decision route called `RevisionRepository.recordApproval`, which already commits the approval row, revision status, task state/version and immutable `design.*` event in one transaction. It then called `TaskRepository.transitionState` in a separate transaction, advancing the task version again and appending a redundant `task.state_changed` event. A new isolated-PostgreSQL regression failed before repair: one approval advanced version 2 → 4 when 2 → 3 was required. The second transition also swallowed errors after a success response.

The route now uses the repository transaction as the sole state transition. The repair budget formerly applied by the second transition was moved into that transaction: after inserting a revision request, the locked task's request count determines `revision_requested` for the first two and `failed_operator` for the third. The regression now proves one version increment and exactly one `design.approved` event; existing cross-Core and repair-budget tests prove the third request is still routed to an operator.

**Verification:** focused Core integration tests passed **3 files / 60 tests** after rebuilding `@hawa/db`; the fixed-tree full suite passed **408 files / 3,076 tests**, with **4 files / 48 tests skipped**. Package/script/test TypeScript checks passed, and blueprint validation reported **741 pass / 0 warning / 0 failure**. An intervening full-suite run loaded the older built `@hawa/db` and failed the two repair-budget tests; it is excluded from the passing evidence. No production deployment, lifecycle cutover, retry-idempotent Desk action, or live approval was tested. R08 remains in progress.

## Third pass — durable Desk action identity

**Source:** `43512ea`; additional restart-shaped test `3bb4794` (2026-09-25). The Desk now sends a UUID `Idempotency-Key` with an approval or revision request and retains it while the screen is mounted if a network error prompts a retry. Core binds the key to the task, revision, authenticated actor and exact request body by a SHA-256 fingerprint. An already committed, identical action returns the existing decision ID; a reused key with different intent returns 409. The repository repeats the lookup under the locked task row, so simultaneous requests serialize to one approval, one event and one version increment. Invalid keys and non-object bodies are refused before any decision write. A client approver without a resolved assigned-client match is refused, including on replay.

The red-before isolated-PostgreSQL test showed a lost-response retry returning 409 after a successful approval. Green-after checks the same key through a **new Core instance**, verifies the original decision ID, unchanged task version and one approval row, and checks a changed payload is rejected. A simultaneous revision-request test produced statuses 201/200 with one ledger row and one version increment. The Desk API test checks that its key reaches Core; escalation replay uses the decision actually stored (`revision_requested`). The exact source tree before the additional test-only commit passed **408 files / 3,080 tests**, **4 files / 48 tests skipped**; the new Core-instance test then passed in isolation. Full source/script/test TypeScript checks and blueprint **741/0/0** passed on the source tree. The action ID is currently kept in the mounted Desk screen, so a browser reload does not preserve it; a refreshed task still reads PostgreSQL truth, but retry equivalence across browser reload is not proven. A freshly constructed Core is not a killed Restate process. No live double click, deployed-image replay, RequestLifecycle gate, or chat approval has been demonstrated. R08 remains in progress.

## Fourth pass — preserve a pending Desk action through tab reload

**Source:** `1d87f3b` (2026-09-25). The third-pass screen-only retention limit is now closed for browsers with Web Crypto and session storage: the pending UUID is stored under a SHA-256 digest of reviewer, task, revision, action and relevant inputs. The key does not expose revision notes in session storage. A retry after a tab reload recovers the same UUID, while changing the note or export selection reserves a different UUID. A successful response removes only the matching reservation. When browser storage or Web Crypto is unavailable, the same mounted screen retains the UUID in memory; reload continuity in that environment remains unavailable and the Core still refuses conflicting intent.

A test simulated a fresh browser module and verified the same UUID, changed-input separation and successful cleanup. The first full-suite run found a lifted WorkScreen test fixture missing the new local guard; affected Desk tests passed after the fixture was updated. The fixed-tree full suite passed **409 files / 3,081 tests**, with **4 files / 48 tests skipped**. Package/script/test TypeScript checks passed. This is browser-level retry identity evidence, not a live browser or deployed-process kill drill. R08 remains in progress until RequestLifecycle owns Desk/chat decisions and the end-to-end replay gate passes.

## Fifth pass — first private, versioned RequestLifecycle office transition

**Source:** `cc55fcd` (2026-09-25). A private `RequestLifecycle.officeDecision` handler now accepts a round-zero **revision request** naming the current task and design revision at expected request revision 2. Its worker-only Core projection locks the request, checks the persisted owner, in-review stage, current task and draft, fences the task version, and commits the append-only approval, task state/event, request revision 3 and hash-bound replay receipt in one PostgreSQL transaction. The task's ordinary legacy approval repository still refuses a call without the matching internal lifecycle request ID. The worker stores the resulting approval ID and request state, and an identical event replays the same result. Changed content under the same action key is refused.

The isolated PostgreSQL test first failed with **404** before the route existed. After implementation it checks wrong worker credential, stale draft, operator role, simultaneous identical calls, changed-content conflict, one task version increment, one approval and receipts at revisions 1/2/3. A worker journal test covers a lost Core answer and a crash after state storage. Focused checks passed **2 files / 5 tests**; TypeScript including test files passed. The first full source run found only a missing route-inventory entry (**415 files / 3,113 tests passed; one inventory failure**). After updating the declared inventory, source `cc55fcd` passed **416 files / 3,114 tests**, with **4 files / 48 tests skipped**. The release manifest and blueprint seal are verified after this evidence update.

**Limit:** The authenticated Desk route still deliberately returns `LIFECYCLE_OWNED` for request-owned tasks. It does not call this private handler; ChatInbox remains `legacy` and lifecycle flags remain off. The worker-only projection trusts its internal actor fields and has no external authenticated Desk identity bridge. This slice handles only a first `revise` decision. Approval/rejection, revision-request structure (scope, category, targets, priority, reuse), requester decisions, subsequent rounds, live Restate process restart and artifact-hash qualification remain open. R08 is **in progress**, and this is not production office-decision admission.

## Sixth pass — signed Desk bridge into the private request owner

**Source:** `33a2fb2` (2026-09-25), ADR-040. The fifth-pass Desk gap is partly closed: for a request-owned task, the signed-in Desk art/creative director or office administrator can now submit the existing `revision_requested` action with a mandatory UUID `Idempotency-Key` and reason. Core derives the reviewer ID and role from the authenticated session, reads the task's persisted request owner, and signs a versioned event with a domain-separated HMAC. A new, permanently bound `OfficeDecisionGateway` is the only public Restate entry for this action; it validates the signature before calling the private `RequestLifecycle.officeDecision`. The object and Core projection retain the current-draft, expected-revision, role, task-version and receipt checks. Core sends an exact retry to the object even after the request advanced to revision 3, so a lost Desk answer returns the original approval. A changed reason under the same action ID is refused. The public ingress receives the signature, not the raw worker credential.

An isolated PostgreSQL integration test exercises the authenticated Desk route, the signed gateway check, the RequestLifecycle handler and Core projection in one local chain. It loses the first Desk response **after** the approval commits, retries through a newly constructed Core app, and sees the same decision with one approval and receipts 1/2/3. An operator and a missing action key are refused before gateway use; changed intent returns 409. A worker test checks tampering, wrong secret and malformed event IDs, and the blue/green service inventory test checks the new permanent name. Focused checks passed **4 files / 16 tests** before a fixture-only security-scan repair, then **3 files / 8 tests** after it. The fixed source suite excluding only the unsealed release-gate file passed **417 files / 3,116 tests**, with **4 files / 48 tests skipped**. TypeScript including tests passed and blueprint validation reported **743/0/0** after the ADR was added. The release manifest and complete exact-tree suite follow this evidence checkpoint. The security hook initially rejected one synthetic fixture literal; it was changed to a constructed fixture, then the scan passed with zero secrets.

**Limit:** This is a local chain with a simulated Restate HTTP gateway, not a running Restate process or deployed worker restart. Only the first `revise` action is implemented. Client approvers and account leads are deliberately excluded until client/project authority is resolved; FR-043 is not fully qualified. The Desk currently supplies a single comment, so FR-042 structured scope/category/targets/priority/reuse remains open. Approval, rejection, requester decisions, subsequent rounds, chat decisions, lifecycle delivery, external receipts, and artifact-hash admission remain open. ChatInbox is still `legacy` and production lifecycle flags remain off. R08 remains **in progress**.
